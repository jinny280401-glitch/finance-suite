## 1. 定位

### 1.1 从（Day 18 v1 前身）
> 金融垂类可信 AI 研究基础设施

### 1.2 到（v1.0）
> **Vera 是面向金融机构的可信 AI 研究基础设施**，通过 **Evidence Layer**、**Trust Gate** 和 **Research Runtime**，让 AI 从"会回答"走向"可验证、可审计、可部署"。

### 1.3 Vera 不是什么

| 不是什么 | 理由 |
|-----|--------|
| 投研数据平台 | 不与 Alpha 派 / Wind / 同花顺 / 东方财富等数据源做能力竞争 |
| 通用 AI 助手 | 不追求对话自然度；追求结论可追溯 |
| 自动化交易系统 | 不提供目标价 / 仓位 / 买卖信号（Trust Gate 硬约束） |
| 数据安全体系 | 不替代机构已有的数据安全 / 合规 / 审计设施 |
| 替代 Alpha / Matt | 不复制投研智能；融合数据 + 智能为可信控制层服务 |

### 1.4 Vera 是什么

- **可信控制层 (Trust Control Layer)**：套在 AI 推理前后的合规与审计基础设施
- **研究流程调度 (Research Workflow)**：把研究任务拆解成可解释的步骤并管理状态
- **证据收口 (Evidence Manifest)**：每条结论绑定 evidence_id + 来源 + 时间
- **企业化接入标准 (Enterprise Integration Contract)**：SSO / RBAC / 脱敏网关 / 审计 / 急停的接口定义

├──────────────────────────────────────────────────────────┤
│                  信任门                                   │  ← 来源校验 / 使用边界 / 输出治理

## 3. 机构安全层（新增）

> **扩展理由**：Day 18 v1 没有企业安全抽象。v1.0 引入此层是因为机构部署需要身份 / 隐私 / 审计边界的标准化——Vera 不实现这些，但定义统一契约以对接机构侧已有系统（受 Matt 双节点架构启发，但适配 Vera 的运行时形态）。

### 3.1 本层原则

```text
Vera 不替代机构安全体系。
Vera 提供标准化接入能力。
Vera 对接机构侧已有设施，不复制其实现。
```

### 3.2 子模块

| 子模块 | 能力 | Vera 的角色 | 状态 |
|------------|-----------|-------------|--------|
| **身份管理** | SSO / OIDC / SAML | 定义统一身份契约；对接机构 IdP | 架构已定义，接口已预留 |
| **访问控制** | RBAC / 角色策略 | 定义基于角色的策略 schema；对接机构 RBAC | 架构已定义，接口已预留 |
| **数据保护** | 数据分级 / 隐私控制 | 为 Evidence 打分级标签；按分级路由 | 架构已定义，接口已预留 |
| **脱敏网关** | 个人身份信息 / 敏感字段脱敏 | **接入机构已有脱敏能力**；预留统一接口 | 架构已定义，接口已预留，运行时待实现 |
| **审计** | 请求追踪 / 操作日志 | 以标准化格式输出审计事件 | 架构已定义，接口已预留 |
| **急停控制** | 一键关停 / 只读降级 | 接收机构管理员急停信号；降级为只读模式 | 架构已定义，接口已预留 |

### 3.3 与机构侧系统的边界

| 机构保留 | Vera 提供 | 双方均不持有 |
|------------------------|-------------------|--------------------|
| IdP（身份源） | 标准 SSO 重定向 / OIDC token 校验 | 无——设计上无重叠 |
| 账号 ↔ UUID 映射 | 审计日志中的 UUID 消费 | 账号存储本身（仅机构持有） |
| 机构已有 RBAC 策略库 | 角色策略消费接口 | Vera 本地 RBAC 库 |
| 机构已有 DLP / 脱敏系统 | 脱敏网关接口 | Vera 自身的 PII 检测（我们没有） |
| 机构已有 SOC / SIEM | JSON 格式审计事件流 | Vera 自身的日志存储（从审计角度看无状态） |
| 机构已有急停面板 | 急停信号消费者 | 自签发急停（机构持有触发权） |

### 3.4 参考模式

- Matt 的双节点拆分（券商业务节点在机房 + 扩展服务节点在合规云）在架构上与本层**兼容**，但 Vera 运行时形态不同。Vera **不**复制 Matt 的硬件规格、供应商选择或商业条款。
- 机构数据驻留要求（机房 / 境内合规云 / 跨境限制）是本层必须尊重但不负责解决的约束。

## 4. 脱敏网关（架构已预留）

### 4.1 状态（约束条款）

```yaml
脱敏能力:
  架构:    已定义
  接口:    已预留
  运行时:  待实现
  生产:    未声明
```

### 4.2 本节做什么

本节定义脱敏的**接入契约**。本节不实现脱敏，不选择脱敏算法，不声称 Vera 目前能检测 PII。

### 4.3 契约面（接口已预留）

| 接口 | 方向 | 用途 |
|-----------|-----------|---------|
| `gateway.desensitization.input` | 入站 | 从机构 DLP 接收已完成脱敏的文本或信源 |
| `gateway.desensitization.output` | 出站 | 透传至 Research Runtime；Vera 不做转换 |
| `gateway.desensitization.audit` | 出站 | 输出事件："请求 X 经过脱敏层 Y" |
| `gateway.desensitization.bypass` | 不适用 | **绕过禁止**——Vera 不绕过机构安全 |

### 4.4 明确不做出的能力声明

- ❌ Vera 有自己的脱敏引擎
- ❌ Vera 自主检测 PII / 敏感字段
- ❌ Vera 清洗用户上传内容
- ❌ Vera 认证机构 DLP 输出

### 4.5 允许做的事（脱敏相关）

- ✅ 输出脱敏发生证据（时间戳 + 层标识符，不含载荷）
- ✅ 阻止数据分级禁止当前用途的研究请求
- ✅ 将机构侧脱敏失败上报至机构审计（Vera 不重试）
- ✅ 维护"Vera 本地不存储 PII"不变式——Vera 状态中存在 PII 即为 bug

### 4.6 参考模式

- Matt 5.1 / 5.2"对外仅传输脱敏数据"+ 内容预过滤（DS4）是一个**具体实现**；Vera 不将 DS4 作为自身能力。上述契约面才是抽象层。

## 5. Alpha / Matt 能力集成设计

### 5.1 定位

```text
Alpha 提供投研智能与数据能力。
Vera 提供金融 AI 的可信控制层与基础设施能力。
两者通过外部智能 Provider 层集成。
Vera 不复制 Alpha 的产品能力；Vera 不替代 Matt 的部署模式。
```

### 5.2 外部智能 Provider 层

| Provider 类别 | 示例来源 | 集成模式 |
|----------------|-----------------|------------------|
| 投研数据库 | Alpha 派 RAG recall / Wind 投研数据库 / 同花顺 iFinD / 东方财富 Choice | 读取 API → Evidence Manifest |
| 公告 | 巨潮 / 上交所 / 深交所 / 港交所 | 事件 API → Evidence Manifest |
| 研报 | Alpha 派研报库 / Wind 研报库 / Choice 研报库 | 搜索/检索 API → Evidence Manifest |
| 调研纪要 | Alpha 派调研管理 / 调研通 | 搜索 API → Evidence Manifest |
| 内部知识库 | 机构内部 RAG | 适配器 → Evidence Manifest |
| 第三方 Agent | Alpha 派 13 种股票 Agent / 其他域智能体 | Agent API → Trust Gate → Research Runtime |

### 5.3 集成流（架构）

```
数据 Provider（Alpha / Wind / 公告 / 知识库 / Agent）
        ↓
   Evidence Manifest
   （每条数据绑定 evidence_id + source + retrieved_at + 完整性）
        ↓
   Trust Gate
   （来源真实 + 时效有效 + 用途合规）
        ↓
   Vera Research Runtime
   （状态机驱动 + 降级策略 + 多智能体协同）
        ↓
   结果 + 能力边界声明
```

### 5.4 集成优先级（设计建议，非承诺）

| 优先级 | 集成 | 状态 | 理由 |
|----------|-------------|--------|-----|
| 高 | Alpha RAG recall → Vera Evidence Layer | 未来 | 补齐数据厚度 |
| 高 | Alpha qa → Trust Gate → Vera 输出 | 未来 | 投研问答 + 可信保障 |
| 中 | Alpha 股票 Agent → Research Runtime 编排 | 未来 | 快速获得 13 种 Agent 能力 |
| 中 | 搜图表接口 → 报告可视化增强 | 未来 | 增强研究报告展示 |
| 远期 | Trust Gate 标准化为 SDK → 反向赋能 Alpha 合规能力 | 未来 | 双向合作 |

以上为**架构优先级**，不是路线图承诺。每项集成都需要按能力成熟度阶梯 §3 获得独立窗口授权。

### 5.5 集成中 Vera 不做的事

- ❌ 直接调用 Alpha / Wind 私有 API（必须经 Provider Architecture v0.1 通道）
- ❌ 把 Alpha 数据直接当作 Evidence（必须经过 Evidence Manifest 包装）
- ❌ 跳过 Trust Gate 直接进入 Research Runtime
- ❌ 把 Alpha 的产品功能宣传为 Vera 自有能力

## 6. 研究证据层增强

### 6.1 估值证据模块（新增）

将原有的单一 PE Band 概念扩展为结构化估值证据模块：

```
估值证据
├── PE Band（历史 PE 区间）
├── PB Band（历史 PB 区间）
├── 历史分位（PE / PB 历史分位）
├── 同业对比（行业比较）
└── 估值溯源（数据来源 + 时间戳）
```

#### 6.1.1 为什么是模块而非单点

单一估值维度只能回答一个问题，无法支撑 AI 研究结论。

```
单一 PE Band 能回答：
    当前估值处于历史什么位置

AI 研究结论需要：
    估值位置
      + 估值依据（指标体系）
      + 数据来源（哪个 provider、何时取到）
      + 比较体系（同业 / 历史 / 行业分位）
      + 计算过程（口径、调整、可复现性）
```

缺失这些维度的情况下，大模型输入只有单一 PE Band 数据，它别无选择，只能要么 (a) 拒绝做估值推理，要么 (b) 凭空编造缺失的维度——后者正是 Evidence Layer 设计之初就要防止的幻觉路径。模块结构让 AI 的输入可审计，从而让输出可治理；单点结构则迫使 AI 从证据流之外补齐信息。

这一扩展是**结构性的**，而非表面的。它不提升预测准确率，不赋予买卖判断能力，不产生投资建议。它提升的是**研究可解释性**、**证据完整性**，降低的是 **AI 输出不可解释风险**。输出治理边界（无目标价 / 无买卖信号）仍然在 Trust Gate 层（§2）执行。

### 6.2 定位

```text
不是预测。
而是：
支撑 AI 投资研究结论的解释证据。
```

### 6.3 能力与证据的区分

| 类型 | 示例 | Vera 的角色 |
|------|---------|-------------|
| 能力 | "Vera 预测某股票 12 个月目标价" | ❌ Trust Gate 硬约束禁止 |
| 证据 | "某股票当前 PE 处于历史 30 分位（来源：XX，2026-07-30 取得）" | ✅ 通过估值证据模块允许 |
| 能力 | "Vera 自动生成投资建议" | ❌ 禁止 |
| 证据 | "Vera 输出该股票的 4 个估值维度的可追溯数据，AI 据此做归纳说明" | ✅ 允许 |

这一区分是**估值证据模块存在的理由**：它给 AI 推理层提供的是可审计的输入，而非可审计的输出。输出治理（无目标价 / 无买卖信号）在 Trust Gate 层执行。

## 7. 企业部署模式

### 7.1 三种部署模式（仅设计阶段）

| 模式 | 描述 | 状态 |
|------|-------------|--------|
| **模式 A — 机构全私有部署** | Vera 完整部署于机构基础设施内；机构拥有全部节点 | 架构已定义 |
| **模式 B — 机构安全节点 + Vera 云端运行时** | 机构运行安全节点（SSO / RBAC / 脱敏 / 审计 / 急停）；Vera 在合规云运行 Research Runtime | 架构已定义 |
| **模式 C — 合规云部署** | Vera 部署于机构认可的合规云；身份 / 数据 / 审计边界由机构定义 | 架构已定义 |

### 7.2 部署中的责任边界

| 承担方 | 职责 |
|-------|----------------|
| **机构控制** | 身份（SSO / OIDC / SAML）· 安全边界 · 审计日志目的地 · 急停触发 · 数据驻留 |
| **Vera 提供** | Research Runtime · Evidence 处理 · Agent 工作流 · Trust Gate 执行 · Evidence Manifest 契约 |

### 7.3 模式选择指南（仅设计）

- 模式 A：适用于数据完全不出机构的场景；机构侧运维负担最高
- 模式 B：适用于机构已有合规云 / 机房，但希望降低研究 runtime 运维负担的场景（受 Matt 启发）
- 模式 C：适用于无自有机房但有合规云账户的机构；部署最快但依赖云合规边界

模式选择是**机构的独立决策**，不属于本架构规格的范畴。本规格仅定义每种模式必须遵守的边界条件。

### 7.4 部署中 Vera 不做出的承诺

- ❌ 硬件规格（CPU / GPU / RAM / 存储 / 网络）——机构特定
- ❌ 云供应商选择（AWS / Azure / 阿里云 / 腾讯云 / 自建）——机构决策
- ❌ 特定 SDK / runtime 版本 —— 部署时按能力成熟度阶梯版本锁定
- ❌ SLA / RPO / RTO 数值 —— 机构特定的 SLA 协商

**估值证据模块子项**（§6.4 详情）：

| 子组件 | 状态 |
|--------|------|
| PE Band | 已有 |
| PB Band | 已有 |
| 历史分位 | UNKNOWN — 依赖 Historical Valuation Data API |
| 同业对比 | 已有 |
| 估值溯源 | 已有 |
| **模块级 MIN()** | **UNKNOWN**（← 拖低整个 Evidence Layer 行 #2 的实际可达成熟度） |

跨窗口晋升规则（来自能力成熟度阶梯）：

```text
claim_maturity = MIN(各子组件成熟度)

最低成熟度组件 = UNKNOWN → 整体声明必须 fail closed
```

因此，即使第 1-8 项各自推进，在第 9 项（生产能力）的每个子组件被独立证明之前，第 9 项始终为 **未声明**。

## 9. 审查清单（冻结前约束条款）

本清单是 v1.0 从设计完成进入冻结状态的关卡。全部通过后才可标记为 FROZEN。

- [ ] **避免把设计写成能力**：每个章节末的状态行是否精确（不是"已定义"即等于"已投产"）
- [ ] **保持 Trust Gate 核心**：Trust Gate 是否仍是第 3 层，不可被降级为可选项
- [ ] **吸收 Alpha / Matt 企业化优势**：Institution Security Layer / Desensitization Gateway / Deployment Model 是否体现两人经验但未照搬
- [ ] **明确 Vera 与投研工具平台区别**：是否每一节都有 NOT 句（什么 Vera 不做）
- [ ] **为后续开发留下接口**：每个 PENDING / RESERVED / Future 标是否对应可识别的下游任务
- [ ] **[新增] 每模块显式计算 MIN()**：每个新增模块（特别是 Institution Security Layer、Desensitization Gateway、Valuation Evidence Module）是否在文档内显式计算 `claim_maturity = MIN(子组件成熟度)`，且最低子组件的 UNKNOWN 状态不得被模块级描述掩盖
- [ ] **[新增] 全文动词扫描**：全文检查"替换 / 升级 / 引入 / 实现"等动词，确保仅用于架构语义（"文档定义了 X 的结构"）而非运行时语义（"系统已完成 X 的实现"）；发现运行态动词的，改写为设计态表述

以上七项全部通过后，v1.0 可标记为 **FROZEN（冻结）**，不是 **CLOSED（关闭）**。CLOSED 意味着生产能力已晋升；FROZEN 仅意味着设计已收口。

## 10. 收束声明

> **Vera 的目标不是成为另一个投研数据平台，而是在金融机构已有数据、安全和业务体系之上，提供可信 AI 研究基础设施，使 AI 研究过程具备证据、边界和责任追溯能力。**

此声明是 v1.0 的锚定点。任何与它矛盾的未来文档（例如将 Vera 视为数据平台）相对于 v1.0 无效。

### 10.1 架构流向（约束条款）

```text
估值证据模块
    ↓
可解释性
信任门
    ↓
输出治理（无目标价 / 无买卖信号）
```

不允许：

```text
估值模块
    ↓
买卖决策
```

信任门始终是 AI 输出边界控制层。新增证据层不稀释输出治理；无论输出来自哪一层，都必须通过信任门的治理关卡。

### 10.2 核心治理公式（约束条款）

```text
架构已定义
    ≠
运行时已实现
    ≠
生产已证明
```

这是整个治理框架的中心纪律，不可协商，是 §8 能力边界表和 §11 签署声明的明确基础。

### 10.3 Vera 定位（锚定，三阶段）

```text
Vera：
    过去：可信 AI 研究助手定位
    现在：面向金融机构的可信 AI 研究基础设施设计蓝图
    未来：通过 Runtime 验证后，逐步形成可部署能力
```

"设计蓝图"一词是刻意的。不得解读为"已具备基础设施能力"。部署能力需要 Runtime 验证执行成熟后才成立；在此之前，本文档仅为设计。

```

  设计：      已完成
  审查：      通过，无结构级修改
  冻结：      审批过渡中

审查通过不自动晋升为冻结。下一步是**审批 → 冻结**，需要独立窗口决策。在此之前：

审查：  通过
冻结：  审批过渡中
```

"审查通过"和"冻结待审批"描述的是同一时间点的状态；冻结转换是被审批关卡的，不是被审查隐含的。
