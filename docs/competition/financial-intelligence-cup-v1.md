## 三层叙事

```
问题：金融 AI 最大风险不是不会生成，而是不可信
  ↓
方案：Trust Gate + Research Runtime
  ↓
价值：让金融机构敢用 AI 做研究
```

### 第一层 · 问题

金融机构不能直接用通用 AI 做投资研究，不是因为模型能力不够：

- **幻觉问题被误诊了**。金融场景的核心风险不是"AI 说错了"，而是"AI 说的时候你不知道它是对是错"。
- **数据新鲜度不可验证**。AI 引用的行情、财报、研报，用户无法判断是实时数据还是过期缓存。
- **证据链不可追溯**。AI 给出一个结论，用户问"为什么"，AI 能解释推理过程，但不能证明引用的数据确实来源于指定信源、且当时确实取到了。

金融行业的容错率不是 95%，是"错了必须能被发现"。

### 第二层 · 方案

Vera 在通用 AI 能力之上，构建了三层可信基础设施：

**① Evidence Manifest（证据身份证）**

每一条进入 AI 上下文的数据，都携带身份凭证：

| 字段 | 含义 |
|---|---|
| `evidence_id` | 证据唯一标识 |
| `source` | 数据来源（provider/type） |
| `retrieved_at` | 获取时间戳 |
| `integrity` | 内容完整性校验 |
| `allowed_use` | 允许的使用层级（仅基本面 / 禁止价格预测 / 禁止投资建议） |
| `blocked_fields` | 被阻断的字段 |

**② Trust Gate（可信门禁）**

回答之前先验证证据边界，不是在回答之后贴风险提示。

AI 的每一次回答，Trust Gate 在上下文进入 LLM 之前完成三个判定：
- **来源是否真实**（provenance — 数据确实来自声明的信源）
- **证据是否仍有效**（validity — 数据仍在 freshness 窗口内）
- **用途是否合规**（boundary — 该数据允许支撑当前层级的结论）

**③ 三级内容治理**

不同场景对可信度的要求不同，Vera 区分三层：

| 层级 | 场景 | 要求 |
|---|---|---|
| 演讲级 | 路演、Demo | 允许修辞和视觉强化 |
| 申请级 | BP、尽调、比赛材料 | 每个数字有出处，每个能力声明可追溯 |
| 审计级 | 生产链路验证 | 每条证据必须有 `evidence_id` + `retrieved_at` + `_qc` 状态 |

### 第三层 · 价值

**对金融机构**：AI 研究助手从"不可验证的黑箱"变成"可审计的研究基础设施"。合规部门可以追溯任何一条结论的证据链。

**对行业**：确立一个原则——金融 AI 的竞争力不是"生成得更像专家"，而是"你说的话我能验证"。

## 六项运行可信治理原则

Vera 采用以下治理原则指导架构设计。这些是**设计原则**，不是已完成的功能清单。

| # | 原则 | 含义 |
|---|---|---|
| 1 | 配置存在 ≠ 运行能力存在 | 配置文件里有，不代表运行时生效 |
| 2 | 凭证存在 ≠ 能力验证通过 | 有了 API key，不代表数据链路正常 |
| 3 | 传输成功 ≠ 业务成功 | HTTP 200 不代表数据正确可用 |
| 4a | 证据存在 ≠ 仍具有效性（设计层） | 数据有 `retrieved_at`，不代表过了 5 分钟还能用 |
| 4b | 判断逻辑存在 ≠ 证据输入存在（运行层） | 代码里有 freshness 检查，不代表生产链路产生了 freshness 数据 |
| 5 | 写入记忆 ≠ 记忆可靠保存 | 记录操作发出了，不代表记录已持久化 |

这六条原则共同定义了 Vera 的 Trust Runtime Architecture：

```
Provenance（来源） → Durability（持久） → Validity（有效）
    "这是什么？"      "曾经是否真实存在？"    "现在是否仍然有效？"
```

三层之间有严格的顺序依赖：不知道来源就不知道是否持久，不知道持久就无法判断是否仍有效。

## Trust Gate：回答之前验证，不是回答之后提示

### 为什么 Trust Gate 的位置很重要

大多数 AI 产品的"安全机制"是后置的——生成回答后，贴一句"仅供参考，不构成投资建议"。这不能阻止错误数据进入回答，只是在错误发生后声明免责。

Vera 的 Trust Gate 插在 **数据召回之后、LLM 上下文注入之前**：

```
用户输入
  ↓
Prompt 组装
  ↓
Memory / Data Recall
  ↓
═══ Trust Gate ═══  ← 在这里验证，不是事后
  ↓
Context Injection
  ↓
LLM
  ↓
Answer
```

Gate 做三件事：
1. 检查每条证据是否有 `source` + `retrieved_at`
2. 判定 `allowed_use` 是否覆盖用户请求的结论层级
3. `_qc.status` 非 `success` 的数据降级展示或阻断

### 当前状态（如实陈述）

| 组件 | 状态 | 说明 |
|---|---|---|
| Evidence Manifest 设计 | ✅ Design PASS | 9 字段 schema 已验证 |
| Trust Gate 逻辑 | ✅ Code exists | 消费端降级逻辑已实现 |
| Freshness 生产写入 | ❌ Not proven | 生产 gateway 尚未产出 freshness |
| Memory Receipt | ❌ Not implemented | 记忆可靠性验证待开发 |
| Runtime 持续验证 | ❌ Not started | 需要生产环境部署后启动 |

**如实表述**：Vera 正在构建 Trust Runtime Architecture，Evidence Manifest 已完成设计验证，Trust Gate 消费端逻辑已实现，生产端数据链路和 Runtime 持续验证是下一步工作。

## 技术架构

```
┌─────────────────────────────────────────┐
│              touziagent.com              │  ← 生产网站
│         Hero 首页 · 工作台 · Demo        │
├─────────────────────────────────────────┤
│           Research Runtime               │
│  ┌─────────┐  ┌────────┐  ┌─────────┐  │
│  │Evidence │  │ Trust  │  │ Content │   │
│  │Manifest │→ │ Gate   │→ │  Gov    │   │
│  └─────────┘  └────────┘  └─────────┘  │
├─────────────────────────────────────────┤
│         Finance Data Gateway            │
│  Wind → Tushare → JoinQuant → AkShare   │
│        （多源降级，_qc 质检）             │
└─────────────────────────────────────────┘
```

数据网关支持 4 层 provider 降级，每次调用返回 `_qc` 质检状态（`success` / `partial` / `failure`），上游据此决定是否降级展示。

## 安全合规

- 项目原始代码未使用开源 AI 框架的默认安全策略，自建了 Evidence Manifest + Trust Gate 治理层
- 所有数据调用可追溯至具体 provider + timestamp
- `_qc` 质检栈覆盖每一次数据获取，失败/降级有明确的 fallback 和展示策略
- 不存储用户个人信息，不涉及客户数据
- 网站 touziagent.com 已上线运行，通过生产环境验证
